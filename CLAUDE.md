# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

**BuenAdoptante** is a pet adoption vetting platform where rescuers can record, search, and share adopter profiles to prevent animals from reaching irresponsible homes. It uses Next.js 15 (App Router) deployed to Cloudflare Pages, with Cloudflare D1 (SQLite) as the database.

## Commands

```bash
# Development
npm run dev               # Start Next.js dev server on port 3000
npm run build             # Production build
npm run lint              # ESLint
npx tsc --noEmit          # TypeScript type check

# Database
npx drizzle-kit generate  # Generate migration from schema changes (after editing src/db/schema.ts)
npx wrangler d1 migrations apply pet-adoption-db-staging --remote   # Apply to staging
npx wrangler d1 migrations apply pet-adoption-db --remote            # Apply to production
npx wrangler d1 execute pet-adoption-db --remote --command "PRAGMA table_info(adopters);"

# E2E Tests
npx playwright test                          # All tests
npx playwright test tests/search.spec.ts     # Single test file
npx playwright test --project=authed         # Admin-authenticated tests
npx playwright test --project=user           # Regular-user authenticated tests
npx playwright test --project=unauthed       # Unauthenticated tests
npx playwright test --project=mobile         # Mobile viewport tests
npx playwright test --ui                     # Interactive UI mode

# Contract App (separate Vite mini-app)
cd contract-app && npm run dev               # Vite dev server on port 5173
```

Playwright requires `AUTH_SECRET` in `.env.local` to sign test JWTs. The webServer command runs `scripts/setup-test-db.js` to seed a fresh local DB before tests start.

## Architecture

### Layer Rules

The codebase follows a strict 4-layer architecture. Violating these causes bugs and makes logic untestable:

```
PRESENTATION  → src/app/**/page.tsx, src/components/
DOMAIN        → src/domain/  (pure functions — NO DB imports, NO server imports)
DATA ACCESS   → src/app/actions/  (server actions — thin orchestrators)
INFRASTRUCTURE→ src/lib/  (logger, audit, R2, Gemini — cross-cutting)
```

Business rules (rating thresholds, flag evaluation, scoring) belong in `src/domain/`, not in server actions. Server actions fetch data then call domain functions. Components receive computed results via props.

### Data Flow

Server Actions in `src/app/actions/` are the primary way data is read and written — prefer these over API routes for in-app operations. API routes in `src/app/api/` serve external integrations (contract app, import endpoints, auth callbacks).

The canonical database accessor is `src/lib/db.ts` — `getDb()`. It auto-detects the Cloudflare context and falls back to a local `better-sqlite3` (`local.db`) in dev. Never instantiate Drizzle directly. In server actions, import via `src/app/actions/_db.ts` which re-exports `getDb` and `getUser`.

### Key Directories

- `src/app/` — Next.js App Router pages, API routes, and server actions
- `src/app/actions/` — Server Actions (the main business logic layer); barrel at `actions/index.ts`
- `src/components/` — React components (client and server)
- `src/db/schema.ts` — Single source of truth for all table definitions
- `src/domain/` — Pure business functions: `constants.ts` (FLAG_REASONS, RECORD_TYPES), `flags.ts` (buildFlags), `ratings.ts` (computeAvgRating)
- `src/config/` — App-level config: `admins.ts` (admin resolution), `features.ts` (feature flags), `constants.ts` (search limits)
- `src/lib/` — Infrastructure utilities (logger, audit, R2, scoring, tokenizer, Gemini)
- `src/i18n/locales/` — EN/ES translation strings (always update **both** when adding keys; see i18n note below)
- `content/` — Keystatic CMS content (guide steps, FAQ, contract template)
- `drizzle/` — Migration SQL files (auto-generated by drizzle-kit)
- `contract-app/` — Standalone Vite app for PDF contract signing
- `.agents/workflows/` — Mandatory agent workflows (deploy, code-quality, schema-sync, ui-review)
- `docs/design-style-guide.md` — Canonical UI design system (8px grid, color tokens, button matrix, typography scale)
- `docs/ux-ui-guidelines.md` — Decision-making framework: principles, patterns, persona conventions, anti-patterns we've walked back
- `docs/D1_COMPATIBILITY.md` — Full D1 SQLite quirks and safe query patterns
- `docs/code_quality_audit.md` — Dated full-codebase audit with security findings and tech-debt roadmap

### Authentication

NextAuth 5 (beta) with Google OAuth. Auth config splits across `src/auth.ts` (runtime) and `src/auth.config.ts` (providers/callbacks, safe for edge). `src/middleware.ts` gates `/my-animals`, `/my-adopters`, `/my-adoptions`, `/settings`, and `/admin`.

Admin access has two tiers: a bootstrap email list in `src/config/admins.ts` (always admin, no DB needed), plus any user with `role='admin'` in the `user_profiles` table. To grant DB-based admin access:
```sql
UPDATE user_profiles SET role = 'admin' WHERE user_id = (SELECT id FROM user WHERE email = 'user@example.com');
```

Feature flag `REQUIRED_SESSION_VERSION` in `src/domain/constants.ts` forces re-auth on deploys when bumped.

### Feature Flags

`src/config/features.ts` — flags are DB-backed (stored in `appConfig` table, togglable via Admin UI) with env var fallback. DB value takes precedence. Current flags: `ENABLE_CONTENT_IMPORT`, `ENABLE_ANIMALS_FOR_ADOPTION`.

### Duplicate Detection

The unified `findAdopters()` function in `src/app/actions/findAdopters.ts` handles both search and duplicate detection via a `mode` parameter:
- `discovery` — Full LIKE search with geo-filter, enrichment, PII masking, and analytics
- `duplicate` — Fast token-index lookup against `duplicate_tokens` table; no auth, no enrichment

Tokenization (`src/lib/tokenizer.ts`) normalizes names (NFD), phones, emails, and social handles. Confidence scoring uses Levenshtein distance + token overlap, bucketed into `high`/`medium`/`low`.

### Database Schema

All tables are in `src/db/schema.ts`. Key tables:
- `adopters` — Core profiles; `status` is a 1–5 rating (1=Dangerous, 5=Excellent); `deletedAt` is soft-delete for merged duplicates
- `adoptions` — Records with `recordType` ∈ `RECORD_TYPES` (adoption, adoption_request, observation, follow_up, returned_pet, available)
- `duplicate_tokens` — Tokenized fields for fast fuzzy matching
- `duplicate_candidates` — Pre-computed pairs with confidence scores
- `adopter_history` — Audit trail of every adopter change
- `appConfig` — Key/value store for feature flags
- `user_profiles` — Extends NextAuth `user` table with `role` and `country`

### Internationalization

The default locale is **`es`** (Spanish), not English. `t()` in `src/context/LanguageContext.tsx` resolves the key against the current locale, falls back to Spanish if missing, then returns the raw key path — never an English string. If you add a key only to `en.ts` and forget `es.ts`, Spanish users see the raw key (e.g. `dashboard.my_key`) instead of anything readable. Always update both locale files together.

### D1 Compatibility

Cloudflare D1 does **not** expand array parameters in `IN` clauses — it generates `IN (?)` with a single bound value regardless of array length, silently returning wrong results. **Never use `inArray()` or `sql\`IN ${array}\``.**

```typescript
// ❌ BROKEN — silently returns wrong results in D1
db.select().from(table).where(inArray(table.id, ids))

// ✅ CORRECT — loop with Promise.all
await Promise.all(ids.map(id => db.select().from(table).where(eq(table.id, id))))
```

When fetching related data for multiple records, fan out with nested `Promise.all` calls. Use `.catch(...)` inline to prevent one failing sub-query from rejecting the whole batch — but **always log the fallback** (see Logging Conventions below). See `docs/D1_COMPATIBILITY.md` for the full reference.

### Logging Conventions

Logger lives at `src/lib/logger.ts` — `logger.info / warn / error / debug`. The `error` method auto-generates an 8-char `errorId` and returns it for surfacing to users.

**Two rules every catch block must follow:**

1. **Re-emit operation context.** If the surrounding handler logs `{ adopterId, user }` on the happy path, the catch must include the same fields. Catch blocks that log only the error message lose all triage context — declare any input variables (e.g. `adopterId`, `actorEmail`) outside the `try { ... }` so they're in scope for the `catch`.

2. **Never silently swallow.** `} catch { /* ignore */ }` and `.catch(() => [])` are landmines — a real DB outage looks like "no results" instead of an alert. The exceptions are: intentional health-check probes (`/api/health`) and SSR-safe `localStorage` reads. Everywhere else, log at `warn` (degraded) or `error` (broken). For D1 fallbacks, use the pattern:
   ```ts
   .catch((e) => {
     logger.warn('descriptiveOp: D1 fallback hit', { adopterId, error: e instanceof Error ? e.message : String(e) });
     return [];
   })
   ```

A reusable helper like `enrichAdopters.ts:logD1Fallback` is fine when the same op repeats inside one function.

**Privacy:** never log full contact info, family members, notes, raw tokens, or other adopters' emails. The actor's own session email is OK as an audit-trail field. `maskEmail` from `src/lib/dates.ts` redacts when needed.

### Constants — No Magic Strings

All flag reasons and record types must come from `src/domain/constants.ts` (`FLAG_REASONS`, `RECORD_TYPES`, `EVENT_TYPES`). Search limits and thresholds live in `src/config/constants.ts`. Never hardcode these strings in server actions or components.

## Deployment

Branch → deploy mapping:
- `master` → `buenadoptante.org` (production)
- `staging` → `staging.verazadoptantes2.pages.dev` (test with OAuth)
- `feature/*` → **not deployed** (no CI job triggers on `feature/*`)

**Every deployment requires a version bump** (see `.agents/workflows/deploy.md` for the full mandatory workflow):
```bash
npm version <version> --no-git-tag-version  # run before committing
git commit -m "v<version>: <description>"
git push origin HEAD:staging                # NEVER push directly to master
```

Lint warnings must not exceed the current ratchet threshold (currently **125**).

**Cloudflare auto-deploy is OFF.** All deploys run through the GitHub Actions pipeline (`.github/workflows/ci.yml`). On push to `staging` or `master` the pipeline runs:

```
build-and-lint  →  migrate-{staging|production}  →  e2e (Playwright, blocking)  →  deploy-{staging|production}
```

The `deploy-*` job runs `npx @cloudflare/next-on-pages` then `npx wrangler pages deploy`. End-to-end takes **~8–15 min**. **Pushing to a branch alone does not deploy** — if any prior job fails (build, lint, migration, e2e), the deploy job is skipped and the branch URL keeps serving the previous build. Track with `gh run list --branch <branch> --limit 3` and `gh run watch <run-id>`.

D1 migrations are applied by the `migrate-*` jobs before deploy — no manual step needed. `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID` GitHub secrets are required.

**Workflow:** feature branch → merge to `staging` → wait for green pipeline → verify on staging URL → PR to `master`.

**Emergency rollback:** Cloudflare Dashboard → Pages → `verazadoptantes2` → Deployments → "Rollback to this deployment" is the fastest path (bypasses CI). Use `git revert` only when you also want migrations/tests to re-run on the rollback.

## Edge Runtime

The homepage (`src/app/page.tsx`) uses `export const runtime = 'edge'` for fast cold starts. Cloudflare Workers compatibility requires the `async_hooks` webpack alias in `next.config.ts`. Don't add Node.js-only APIs to edge-runtime pages.

## Content Management

Guide content (steps, FAQ, benefits) is managed via Keystatic CMS (`keystatic.config.tsx`). In dev it reads from the `content/` directory directly. In production it reads from GitHub. The `/keystatic` route is the CMS admin UI.

## Agent Workflows

`.agents/workflows/` contains mandatory procedural workflows that agents must follow:
- `deploy.md` — Version bumping, CHANGELOG, staging-first deployment, forbidden master-push rules
- `code-quality.md` — Pre-commit checklist (TSC, lint ratchet, domain layer compliance)
- `schema-sync.md` — Run after any `src/db/schema.ts` change to keep local D1 in sync
- `ui-review.md` — Design compliance against `docs/design-style-guide.md`

`.agents/plans/` and `.agents/audits/` store feature implementation plans and post-mortems.
